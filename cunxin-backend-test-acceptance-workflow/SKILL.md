# Cunxin Backend Test Acceptance Workflow

## Overview

本 Skill 只适用于当前项目的 Spring Boot 后端代码测试验收。

本 Skill 的核心目标不是泛泛而谈“需要测试”，而是把后端代码改动后的测试闭环拆解到可执行粒度。

只要涉及后端代码改动，默认都要进入本 Skill，完成以下动作：

1. 判断是否允许跳过测试
2. 执行编译校验
3. 在 `单元测试` 和 `接口测试` 之间做有依据的决策
4. 先按功能维度拆解测试场景与预期结果
5. 输出具体可执行测试内容
6. 明确每个功能场景的实际结果、测试缺口与剩余风险

## Trigger Conditions

以下场景默认触发本 Skill：

- 新增、修改、删除后端 Java 代码
- 修复后端缺陷
- 重构后端实现
- 修改 Controller、Service、Manager、Repository、Mapper、XML、配置类、任务调度、消息处理等后端代码

以下场景默认不触发本 Skill：

- 纯文档修改
- 纯注释修改
- 纯格式整理且无代码行为变化

## Hard Rules

- 只要是后端代码改动，就不能直接交付，必须完成测试闭环或明确记录“按用户要求跳过测试”。
- 测试闭环必须先做编译校验，再做功能验证。
- 功能验证只能得出以下三种结论之一：
  - `执行单元测试`
  - `执行接口测试`
  - `按用户要求跳过测试`
- 除用户明确要求不测试外，不得自行给出“无需测试”的结论。
- 单元测试必须基于当前项目技术栈，兼容 `Spring Boot 2.0.5 + JUnit`。
- 接口测试必须输出完整 `curl`，且必须可覆盖当前接口的真实请求方式与参数结构。
- 不论选择单元测试还是接口测试，都必须先按功能维度说明本次改动测了什么，至少包含：功能点、测试场景、验证内容、预期结果、实际结果。
- 功能维度说明必须优先使用业务语言或用户能直接理解的表达，不得只写测试类名、方法名、接口路径、HTTP 状态或“happy path”。
- 若测试所需信息不完整，必须停下来请求用户参与，不得编造参数、鉴权或环境地址。
- 不得用日志打印、临时 main 方法、无断言代码、手工点点点结果代替测试结论。

## Workflow

### 1. 建立上下文

- 先读取：
  - `../../../docs/BACKEND.md`
  - `../../../docs/backend-rules/01-tech-stack.md`
  - `../../../docs/backend-rules/08-test-acceptance-best-practice.md`
- 读取当前需求、当前改动范围和已确认结论。
- 基于当前改动先拆出“功能点 -> 测试场景 -> 预期结果”的初始清单，作为后续测试执行和结果回填的骨架。
- 识别本次改动落在哪些后端层次：
  - `Controller`
  - `Service`
  - `Manager`
  - `Repository`
  - `Mapper / XML`
  - 配置类 / 拦截器 / 定时任务 / 异步逻辑
- 若当前任务存在 `task.md`、`tasks.md` 或 `task-xx-<topic>.md`，读取当前任务文档，确认测试结果要回填到哪里。

### 2. 先判断是否允许跳过测试

- 检查用户是否明确表达以下意思之一：
  - 不要测试
  - 跳过测试
  - 本轮不用测
  - 只改代码不要跑测试
- 若用户明确要求不测试，则：
  - 不执行编译校验、单元测试或接口测试
  - 输出“按用户要求跳过测试”
  - 必须同时写明：
    - 用户要求
    - 被跳过的测试项
    - 当前风险
  - 若存在 task 文档，仍需把跳过测试及风险记录进当前 task
- 若用户没有明确要求跳过，则继续后续步骤。

### 3. 执行编译校验

- 只要没有被用户明确要求跳过测试，就必须先做编译校验。
- 编译校验目标：确认本次改动没有引入编译错误。
- 优先根据当前任务影响模块选择最小必要的 Maven 编译命令。
- 若能明确模块边界，则优先按模块执行；若无法明确模块，则说明原因，并执行当前可行的最小编译校验。
- 输出时必须写明：
  - 执行了什么编译命令
  - 是否通过
  - 若未执行，原因是什么

示例输出格式：

```md
## 编译校验

- 命令：`mvn -pl <module> -am test-compile`
- 结果：通过 / 未通过 / 未执行
- 说明：...
```

### 4. 做测试决策

在编译校验之后，必须在 `单元测试` 和 `接口测试` 中二选一，并给出依据。

#### 4.1 单元测试决策依据

满足以下多数条件时，优先选择单元测试：

- 改动核心在 `Service`、`Manager`、工具类、校验器、转换器
- 目标是验证规则逻辑、分支判断、参数校验、对象转换、聚合计算
- 本次改动不以 HTTP 契约为核心验证对象
- 可以通过 Spring Boot 测试上下文、mock 或依赖替身稳定覆盖

#### 4.2 接口测试决策依据

满足以下多数条件时，优先选择接口测试：

- 改动直接影响 `Controller` 暴露的 HTTP 行为
- 需要验证入参、出参、字段语义、错误码、鉴权、路径或请求方式
- 需要验证 `ApiResult` 包装或真实 HTTP 返回
- 通过 HTTP 调用比单元测试更直接覆盖本次改动目标

#### 4.3 禁止的决策方式

- 不能因为“写单测更方便”就默认单元测试
- 不能因为“接口能调通”就跳过单元层验证的依据说明
- 不能说“都测一下”但不给优先级和可执行内容
- 不能说“无需测试”除非用户明确要求跳过

#### 4.4 先拆功能维度测试清单

- 在确定测试方式后、执行具体测试前，必须先从业务功能角度列出本次改动测了什么。
- 至少包含：
  - 功能点
  - 测试场景
  - 验证内容
  - 预期结果
- 描述必须通俗，优先让不了解代码实现的人也能看懂。
- 不允许只写 `OrderServiceTest`、`/cart/useCoupon`、`成功路径` 这类技术标签而不解释其业务含义。

### 5. 执行单元测试

当决策结果为 `单元测试` 时，必须执行以下步骤：

#### 5.1 明确测试目标

- 先列出本次单元测试对应的功能点、测试场景、验证内容和预期结果。
- 再写明本次单元测试要覆盖哪个类、哪个方法、哪类行为变化。
- 至少列出：
  - 成功路径
  - 关键分支
  - 边界条件
  - 异常或错误输入

#### 5.2 明确技术前提

- 测试实现必须兼容 `Java 1.8 + Spring Boot 2.0.5`。
- 测试框架按 `JUnit` 体系编写；若项目已有现成测试写法，必须优先保持一致。
- 若依赖 Spring 上下文、数据库、外部服务、Mapper、Repository，必须说明使用：
  - mock
  - stub
  - Spring Boot 测试上下文
  - 其他隔离方式

#### 5.3 产出要求

- 单元测试必须有真实断言。
- 不允许仅打印结果。
- 不允许只覆盖 happy path。
- 测试结果必须逐项回填到功能维度场景，写明实际结果与结论。

#### 5.4 执行要求

- 给出具体执行命令。
- 若无法执行测试命令，必须写出原因与风险。

示例输出结构：

```md
## 测试决策

- 结论：执行单元测试
- 依据：本次改动集中在 `OrderService#calculatePrice`，核心是规则判断，不涉及 HTTP 契约

## 功能维度测试说明

| 功能点 | 测试场景 | 验证内容 | 预期结果 |
| --- | --- | --- | --- |
| 订单优惠计算 | 满足优惠门槛时下单 | 优惠规则正确生效 | 订单金额按规则扣减 |
| 订单优惠计算 | 不满足门槛时下单 | 不应错误使用优惠 | 订单金额保持原值 |

## 单元测试计划

- 测试类：`OrderServiceTest`
- 覆盖方法：`calculatePrice`
- 覆盖点：
  - 正常价格计算
  - 优惠为空
  - 数量为边界值
  - 非法输入异常

## 执行命令

- `mvn -pl <module> -am -Dtest=OrderServiceTest test`

## 测试结果

| 功能点 | 测试场景 | 实际结果 | 结论 |
| --- | --- | --- | --- |
| 订单优惠计算 | 满足优惠门槛时下单 | 已验证，金额按规则扣减 | 通过 |
| 订单优惠计算 | 不满足门槛时下单 | 已验证，未发生错误扣减 | 通过 |
```

### 6. 执行接口测试

当决策结果为 `接口测试` 时，必须执行以下步骤：

#### 6.1 先确认接口信息是否完整

- 在确认接口信息前，先列出当前接口测试要验证的功能点、测试场景、验证内容和预期结果。
- 每条 `curl` 都应能映射到明确功能场景，不得只剩接口路径和参数。
必须确认以下信息是否已明确：

- 环境地址
- 请求方式
- 接口路径
- 必要请求头
- 鉴权方式
- Query 参数或请求体
- 必要前置数据

#### 6.2 信息不完整时的处理

- 若以上任一关键项不明确，必须暂停并向用户请求补充。
- 请求补充时必须明确指出缺什么，不得笼统说“参数不全”。

示例：

```md
当前无法生成可执行 `curl`，缺少以下信息：

- 测试环境 base URL
- 登录态或 token
- `orderId` 的可用测试值
```

#### 6.3 产出完整 curl

- 必须输出至少一条成功场景 `curl`
- 必须输出至少一条失败或边界场景 `curl`
- `GET` 场景使用 query string
- `POST` 场景使用完整 JSON body
- 请求头必须写全
- 若需要 token，必须保留明确占位符，不得伪造
- 接口测试结果必须逐项回填到功能场景，写明实际结果与结论，不得只写“返回 200”。

示例输出结构：

````md
## 测试决策

- 结论：执行接口测试
- 依据：本次改动直接影响 `PositionPrinterManageController` 的 HTTP 入参与返回结构，重点是接口行为验证

## 功能维度测试说明

| 功能点 | 测试场景 | 验证内容 | 预期结果 |
| --- | --- | --- | --- |
| 打印机详情查询 | 查询存在的打印机 | 返回打印机详情 | `ApiResult` 成功且返回详情数据 |
| 打印机详情查询 | 缺少 id 参数 | 参数校验正确拦截 | 返回失败结果或参数错误信息 |

## 成功场景 curl

```bash
curl -X GET "{{baseUrl}}/cloudapi/printer/detail?id=123" \
  -H "Authorization: Bearer {{token}}" \
  -H "Content-Type: application/json"
```

## 失败场景 curl

```bash
curl -X GET "{{baseUrl}}/cloudapi/printer/detail?id=" \
  -H "Authorization: Bearer {{token}}" \
  -H "Content-Type: application/json"
```

## 测试结果

| 功能点 | 测试场景 | 实际结果 | 结论 |
| --- | --- | --- | --- |
| 打印机详情查询 | 查询存在的打印机 | 已验证，返回成功并带详情数据 | 通过 |
| 打印机详情查询 | 缺少 id 参数 | 已验证，返回参数错误 | 通过 |
````

### 7. 回填测试记录

- 若存在 task 文档，必须把以下内容写入当前 task 的测试验收部分：
  - 是否跳过测试
  - 编译校验结果
  - 测试决策与依据
  - 功能点与测试场景
  - 每个场景的预期结果与实际结果
  - 具体命令或 curl
  - 已验证项
  - 未验证项
  - 剩余风险
- 若不存在 task 文档，则在最终交付中完整输出上述内容。

### 8. 最终输出结构

执行本 Skill 后，输出必须至少包含以下章节：

1. `测试前提`
2. `是否跳过测试`
3. `编译校验`
4. `测试决策与依据`
5. `功能维度测试说明`
6. `测试执行内容`
7. `测试结果`
8. `测试缺口与剩余风险`

### 9. 完成标准

只有满足以下条件，才可视为测试闭环完成：

- 已明确是否按用户要求跳过测试
- 若未跳过，已完成编译校验或明确记录无法执行原因
- 已在单元测试或接口测试之间做出有依据的决策
- 已按功能维度说明本次改动测了什么，并逐项给出场景结果
- 已输出可执行的测试命令或完整 curl
- 已明确测试结果、测试缺口和剩余风险
