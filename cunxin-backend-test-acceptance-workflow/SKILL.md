# Cunxin Backend Test Acceptance Workflow

## Overview

本 Skill 只适用于当前项目的 Spring Boot 后端功能测试验收，不适用于前端页面、UI 交互或纯前后端联动场景。

触发时机如下：

- 后端新增功能
- 后端修改功能
- 修复后端缺陷
- 后端重构且行为发生变化

只要后端代码行为发生变化，就不能在实现后直接结束，必须完成本 Skill 定义的测试验收流程。

## Workflow

### 1. 建立上下文

- 先定位当前任务对应的 `work_id`
- 若当前任务存在 `docs/task-docs/active/<work_id>/task.md` 或 `tasks.md` / `task-xx-<topic>.md`，必须读取当前任务文档并确定当前执行的 task
- 结合代码变更范围，识别受影响的后端模块，包括但不限于：
  - `Controller`
  - `Service`
  - `Manager`
  - `Repository`
  - `Mapper / XML`
  - 数据库表
  - 缓存
  - 消息
  - 第三方调用
  - 异步任务 / 回调 / 定时任务
- 明确本次是否发生了接口行为变化、数据库写入变化、状态流转变化或副作用变化
- 不要只根据改动文件数量判断风险，必须根据行为变化和副作用判断风险

### 2. 判断影响范围

按以下方式识别后端影响范围：

- 接口契约：入参、出参、错误码、字段语义、`/cloudapi` 路径
- 业务逻辑：校验、状态流转、规则判断、权限判断
- 数据访问：SQL、Repository、Mapper/XML、数据库写操作、副作用
- 一致性：事务、幂等、重试、补偿、回滚
- 外部依赖：缓存、MQ、第三方服务、回调、异步任务、定时任务

### 3. 判断风险等级

使用以下标准：

| 风险等级 | 判定标准 | 最低要求 |
| --- | --- | --- |
| 低风险 | 纯校验、转换、工具类、无副作用只读查询、无接口契约变化的小范围逻辑调整 | 快速测试 + 验收清单 |
| 中风险 | 单模块业务逻辑变化、单表写操作、已有接口行为增强、缓存更新、已有查询条件变化 | 快速测试 + 集成测试或接口验证 + 验收清单 |
| 高风险 | 接口契约变化、多表更新、事务、状态流转、订单/金额/权益、异步任务、回调、第三方依赖、权限、幂等、并发、批量 | 快速测试 + 集成测试 + 接口验证 + Smoke/人工验收项 + 验收清单 |

以下情况默认上调风险等级：

- 涉及数据库写操作、状态变化、外部依赖、异步任务：至少 `中风险`
- 涉及接口契约变化、多表事务、金额、订单、权益、核心流程、并发、批量：按 `高风险`

### 4. 决定测试层级

测试层级必须按后端变更类型选择，不得所有任务都写成同一种测试。

- 后端快速测试：校验器、转换器、工具类、纯规则逻辑、轻量业务分支
- Spring Boot 集成测试：Controller、Service、Repository、数据库读写、事务、关键业务链路
- 接口验证：请求参数、响应结构、错误码、字段语义、`ApiResult` 包装、`/cloudapi` 路径
- 数据副作用验证：数据库写入、状态流转、缓存更新、消息投递、回调结果
- Smoke / 人工验收：高风险需求在测试环境验证关键主流程

选择时遵守以下原则：

- 只改纯规则逻辑时，优先补后端快速测试
- 改动 Controller / Service / Repository 且行为发生变化时，至少补集成测试或接口验证
- 涉及数据库写入、事务、多表关系时，必须补集成测试和数据副作用验证
- 涉及接口契约、字段语义或错误码变化时，必须补接口验证
- 涉及异步任务、回调、第三方依赖、并发或批量时，必须补专项验收项
- 手工调试脚本只能用于联调或排障，不得算作自动化测试门禁

### 5. 补齐验收清单

- 若当前任务存在 task 文档，必须更新当前 task 对应的验收清单
- 若当前工作被拆分为多个 task，必须至少更新当前子任务文档；必要时同步更新 `tasks.md` 总体进度说明
- 若当前任务没有 task 文档，必须在最终交付中单独输出完整验收清单、测试缺口和剩余风险
- 验收清单模板使用 `references/acceptance-checklist-template.md`

至少覆盖以下内容：

- 成功路径
- 输入校验与错误码
- 边界条件
- 异常路径
- 回归影响点

按影响范围追加：

- 接口契约与字段语义
- 数据库副作用
- 事务边界与回滚
- 幂等性
- 异步任务 / 回调 / 消息
- 并发 / 批量
- 第三方依赖失败场景

### 6. 执行与输出

输出结果时，必须明确写出：

- 后端影响范围
- 风险等级与判断依据
- 已补齐或已执行的测试层级
- 已更新的 task 文档位置或最终交付中的验收清单位置
- 当前测试缺口和剩余风险

如果当前环境无法补齐自动化测试，不得假装完成，必须补充：

- 缺失的测试项
- 无法补齐的具体原因
- 当前风险
- 替代性的人工验收方案

### 7. 项目内特殊约束

- 不要依赖默认 `prod` profile 作为测试前提
- 不要依赖真实线上数据或人工维护的固定生产 ID
- 不要把无断言调试类、临时 main 方法或脚本输出当作自动化测试结论
- 不要只验证 happy path
- 不要只写“已自测”，必须列出具体验收项和测试结论

### 8. 完成标准

只有满足以下条件，才可以把后端任务视为完成：

- 已明确后端影响范围
- 已完成风险分级
- 已确定并执行对应测试层级
- 已更新当前 task 验收清单，或在最终交付中补充完整验收清单
- 已明确自动化验证结果、人工验收项、测试缺口和剩余风险
